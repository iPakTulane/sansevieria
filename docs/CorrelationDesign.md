# Stateful Service Interaction & Correlation

This document provides absolute insight into how the Sansevieria distributed system tracks transactions securely across distinct architectural boundaries—from public APIs spanning deep into RabbitMQ payloads, to native BPMN flows, and ultimately committing to PostgreSQL natively.

## 1. The Correlation Key (`correlation_id`)

In microservice models, isolated services typically have zero implicit local memory of what actions other services perform natively. The backbone tracking mechanism linking an isolated RabbitMQ string payload to a PostgreSQL row operation is uniquely enforced using a single **Correlation Identifier**.
- Here, the business identifier natively driving the operations is strictly mapped to the **`order_id`** (e.g. `ORD-000123`). 
- Generated by FastAPI during checkout (`/api/checkout`), `order_id` natively becomes a distinct global signature dynamically propagated explicitly into all message headers defining `correlation_id=ORD-000123`.

## 2. Linking Messages, Workflow, and Database

Tracking transitions effectively relies explicitly on stuffing the `.correlation_id` across explicit layers consistently:

### API Level (FastAPI)
- During checkout, the DB allocates a row tracking natively as `Order` with status `PENDING`. This explicit primary key instantly wraps into the JSON dict variable headers mapping natively:
  ```json
   { "event": "ORDER_CREATED", "order_id": "ORD-000123" }
  ```

### Messaging Level (RabbitMQ)
- As the Producer executes `publish_message()`, it deliberately inserts `correlation_id="ORD-000123"` into the formal protocol headers for AMQP natively!
- Later, any decoupled Python Consumer catching this blob automatically unpacks the native RabbitMQ headers specifically routing logs seamlessly: `logger.info(correlation_id=ORD-000123)`.

### Orchestration Level (Camunda BPMN)
- At the consumer step, the `.businessKey` hook triggers an execution directly inside Camunda via `start_process_instance(business_key=correlation_id)`.
- Inside the workflow engine, this is embedded deeply into internal variables dynamically matching execution threads globally.
- As the parallel poll loops repeatedly invoke `fetchAndLock` tasks off the engine, Camunda strictly bounds the task response natively supplying this identical `businessKey` explicitly! 

### Database Mutations (PostgreSQL)
- The executing task (via `workflow_service.py`) dynamically extracts the token explicitly.
- The Python method natively executes `update_order_state(db, order_id_str, "PROCESSING", correlation_id=ORD-000123)`.
- Row lookup locates the exact record universally without tracking memory strings locally updating state consistently.

## 3. Handling Concurrent Requests

In heavily distributed multi-node architecture, native systems could inadvertently attempt processing duplicate `businessKeys` or overlapping state hooks wildly crashing logic.

### Concurrency Protection & Idempotency:
By tightly combining the DB limits natively with our robust correlation wrappers, we guarantee 100% data integrity:
1. **Row-level Pessimistic DB Locking**: `order_state_service.py` heavily protects atomic updates using SQLAlchemy's explicit `with_for_update()` queries. 
   - If two worker threads attempt to modify identically correlated `order_id` state flags natively, the first connection forces explicit DB Row Locks preventing overlaps implicitly! 
   - The second thread will naturally hang natively blocking logic until exactly finished, safely averting dirty writes dynamically!
2. **Idempotent Validations**: Natively matching expected inputs across state hooks guarantees robust behavior explicitly.
   - For example: if Camunda requests to flip the `PENDING` -> `PROCESSING` transition for explicit `order_id` multiple times, the strict `order_state_service` instantly flags a duplicate invalidation (`"Order cannot transition from PROCESSING to PROCESSING"`), natively dropping the event cleanly avoiding total infrastructure collapses or silent double-billing logically!
